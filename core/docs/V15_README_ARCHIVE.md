# Allocation Core V15｜先看这里（零基础版）

**定位**：一套可以嵌入各类财务、成本、计划和经营系统的通用分摊后端。前端只是试算和规则生成辅助工具。所有演示数据都是虚构的。

## 一、请先做这四个动作

1. 下载完整 ZIP，在 Windows 上右键选择**全部解压**（不要在压缩包里直接运行）。
2. 双击 **`tools/Allocation_Studio_V15_Offline.html`**，建议使用 Edge 或 Chrome。
3. 点击顶部四种示例：**双因子 / 三因子 / 两步骤 / 分叉汇合**，输入自己的模拟金额、权重或份额，右侧立即看到试算结果。
4. 如果想查看正式后端结果，直接双击以下脚本之一（无需安装 Python）：
   - `11_Windows_Two_Drivers.bat` 双因子（75% 材料量 + 25% 收入）
   - `12_Windows_Three_Drivers.bat` 三因子（50% 材料量 + 30% 收入 + 20% 订单量）
   - `13_Windows_Two_Stages.bat` 两步骤（工厂 → 系列 → 商品）
   - `14_Windows_Split_And_Merge.bat` 两条路径分摊后汇合

这些脚本会自动：检查规则和 CSV 表头 → 解释分摊链 → 执行后端 → 输出分摊前后对照。输出在新建的 `v15_runs/` 文件夹里，避免覆盖之前的结果。

**如果窗口出现故障**：把 `logs/v15_latest.log` 提供给实施人员；启动脚本使用 ASCII 文件名，保留 CMD 窗口。

## 二、四个示例到底算了什么？

| 场景 | 数学含义 | 默认结果 |
|---|---|---|
| 双因子 | 1000 元，75% 按材料量 8:2，25% 按收入 5:5 | 商品A 725 / 商品B 275 |
| 三因子 | 1000 元，50% 材料 8:2、30% 收入 5:5、20% 订单 1:4 | 商品A 590 / 商品B 410 |
| 两步骤 | 1200 元 → 系列甲/乙按工时 1:2 → 四商品按系列内销量 | 商品A 100 / B 300 / C 400 / D 400 |
| 分叉合并 | 1000 元先分成 75% 材料路径与 25% 收入路径，合并 SKU | 商品A 725 / 商品B 275 |

**“双因子”与“分叉合并”默认结果相同，但算法结构不同**：双因子在同一个阶段由两条 Allocation 权重规则分配；分叉合并是 DAG 的两条独立阶段路径，再做结果汇合。这两种都支持，适用于不同的后续可塑链路。

## 三、Total、As Is、Source 只需要理解这三句

- **AS_IS：按当前维度成员分别归集**，例如工厂甲和工厂乙不混在一起。
- **TOTAL：先不区分这个来源维度**，例如将原始 SKU 汇总后再往具体 SKU 分摊。
- **SOURCE：目标维度沿用来源成员**，它要求来源该维度用 **AS_IS**，不能用 TOTAL。

正确组合（最常见）：

| 想实现的业务 | 来源规则 | 目标规则 |
|---|---|---|
| 工厂内分别分摊，不跨工厂 | plant = AS_IS | plant = SOURCE |
| 科目内分摊，不跨科目 | account = AS_IS | account = SOURCE |
| 原始 SKU 合并后重新分到商品 | sku = TOTAL | sku = INCLUDE（选择商品范围） |
| 将来源系列金额分到其下商品 | family = AS_IS；sku = TOTAL | family = SOURCE；sku = INCLUDE |

凡是声明为**守恒维度**（例如工厂、期间、科目）的维度，必须用 **AS_IS + SOURCE**。前端示例已经替你配好，无需手工填。

## 四、分摊前后对比怎么看？

执行每个 BAT 后，打开两个 Excel 文件：

- `results.csv`：每一条分摊明细（双因子下，同一个商品可有**来自两种驱动的两行**，这不是重复分摊）。
- `comparison.csv`：按科目和期间分别汇总来源金额、结果金额和差额。查看末尾 `__TOTAL__` 行，默认案例差额为 **0.00**。

其他证据：`ledger.csv` 记录每条目标对应的驱动及金额；`reconciliation.csv` 记录金额池级守恒检查；`source_to_pool.csv` 记录来源金额到金额池的关联。

**不要把 SKU 级前后差额误认为错误**：分摊前可能只有“待分配”一个商品成员；分摊后才落到商品A/B。系统会保留来源真实坐标，不会伪造分摊前 SKU 金额。优先按 `account,period` 等共同粒度核对。

## 五、把网页里改好的规则给后台运行

1. 在离线页面切换一个案例，修改金额、份额、各目标的分摊依据。
2. 如果份额不是 100%，页面会停止导出并给出明确报错；修改正确后点击**下载可运行规则包**。
3. 解压该 ZIP，将本发行包的 `alloc_windows_amd64.exe` 复制进新解压的文件夹。
4. 双击规则包里自带的 `Windows_Run_Example.bat`。
5. 打开生成的 `output/run_*/results.csv` 和 `comparison.csv`。

网页导出的 ZIP 包含当时界面里的规则 JSON 和金额/驱动 CSV。后端会重新验证和计算，网页不是权威核算源。

## 六、新公司接入的简单流程

1. **定义真实维度**：如 period/account/region/brand/sku/channel，自由替换，不固定汽车维度。
2. **准备金额 CSV**：每条费用带相关维度与 `amount`。
3. **准备驱动 CSV**：销量、收入、工时、订单等数值列；不必为了 100 个科目复制 100 遍共享销量。
4. **选择一个示例 rule.json 作为模板**，修改 `dimensions`、`stages`、`datasets` 和来源/目标规则。
5. 运行 `alloc_windows_amd64.exe doctor rule.json` 检查字段及数据文件，再运行 `validate`、`run` 和 `compare`。
6. **输出给现有系统**：Java/ Python/ HTTP / 文件 ETL 都可以调用同一个后端，无需分别重写算法。

详细开发规范见 `docs/02_INTEGRATION_GUIDE_CN.md`。完整引擎支持多步、多因子、分叉、合并、磁盘驱动索引、检查点、并发等能力；简洁网页只演示四种预设场景，并非覆盖所有复杂规则的无代码编辑器。

## 七、版本边界

V15 的核心改进是**标准示例 + 可理解的规则试算与下载 + 数据就绪检查 + 分摊前后汇总报表**。核心性能架构继承 V14，本次没有新的百万行基准结果，不应虚称速度大幅提升。审批功能未添加；企业级数据库事务、全自动无代码复杂 DAG 编辑仍属于后续工作。

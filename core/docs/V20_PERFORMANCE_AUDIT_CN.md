# Allocation Core V20：严格技术审计与性能实测

## 改动范围

本版沿用 V19 `allocation-ir/2.0`、多步骤 DAG、数值分配与最大余数、Driver 索引、阶段检查点、HTTP 服务及压缩/随机血缘工具。**原有金额算法文件不修改**。新增 `internal/vault` 和 CLI `vault`，并提供数据库批量导入的标准化数据出口。

V19 的 `trace_packed_v19` 仍是可以从审计证据重新生成的索引，V20 默认不将其永久归档。V20 管理的是**历史结果和证据的生命周期**，不是更换分摊算法。

## 三种节省空间来源

1. 原始 CSV 进入 Vault 时使用标准库 gzip，无损恢复。
2. SHA-256 内容寻址：不同场景/版本出现完全相同的文件时，物理文件只存一份。
3. 临时版本保留期：可以在安全预览后删除不再需要的 draft 元数据，并回收无人引用的对象；`official` 始终保护。

**没有假设不同版本的全部计算结果相同。** 相似但不完全相同的百万行 CSV，在当前 V20 中仍是不同对象；进一步增量/块级去重属于未来版本。

## 实测口径

基于 V19 实际执行生成的**两阶段 120 万条结果**（合成数据），采用 V20 `vault add` 重复登记相同内容为两个试算版本和一个正式版本。Linux 容器本地文件系统，Go 标准库 gzip 最快档。

- 单次现有输出约 145.38 MB。
- 3 次登记逻辑输出总量 436,147,332 B。
- Vault 物理对象总量 46,280,190 B。
- 相同内容只存一份（7 个唯一对象）；节省来自**压缩与完全相同字节去重的共同效果**。
- 首次登记约 1.81 s；后续复用约 1.36–1.39 s。耗时包括读取并校验已有压缩证据；这里不是分摊计算加速。
- 在这个场景下，预览删除旧 trial 时释放字节为 0，因为其对象仍被其他运行共享。

以上只代表这一组合成样例和环境。**当每个试算版本结果数据变化较大时，去重收益会明显下降**；`official` 长期保留也仍占用磁盘。

## 稳定性约束

- 只允许 `run_summary.json` 中状态为 `PASS` 的运行登记归档。
- 保留 Excel BOM / 原始压缩数据字节与哈希；恢复到新目录时拒绝覆盖已有文件。
- V18+ 的证据 manifest 在登记前先执行完整校验。
- 已存在的 blob 再次注册时重新校验哈希，不盲目相信磁盘文件名。
- `prune`/`release-source`/`gc` 默认 dry-run；`--apply` 才执行。
- 正式版本受清理策略保护；可回收对象只在**所有仍保留的运行记录均不引用它时**删除。
- 原始结果与 Vault 中哈希不符，拒绝释放原始文件。
- 磁盘维护锁是单机、协作式互斥；不是跨主机分布式事务锁。
- 对抗恶意人员修改仓库 JSON 不在 SHA-256 本身的防护范围内；外部签名/WORM 尚未实现。

## 后续最重要的缺口

1. 不同版本之间的**块级去重与增量数据表示**，必须证明可精确恢复并控制引用管理复杂度。
2. 大规模真实数据库 COPY/批量落地压力测试；当前只有离线批量 CSV 准备，没有生产 DB 集成。
3. 归档冷存储后端（S3/MinIO 等），跨机器一致性、安全权限和访问审计。
4. 生命周期策略与服务端持久任务管理统一；目前为独立可选 CLI，而非自动后台清理。
5. 按场景/日期/科目等增量复算，应先定义业务语义和输入变更边界，不能盲目复用旧账。
6. 输入快照与归档结果的整体可重放性，需要纳入统一运行包协议。

## 数据库批量导出基准（不是数据库入库耗时）

从上述已归档的 120 万行 `results.csv` 直接运行 `vault export-db`，生成 5 列标准批量导入文件：

- 最终 CSV 共 **1,200,000 行**，文件大小约 **287 MB**。
- Linux 测试容器实测生成约 **4.93 秒**，进程峰值 RSS 约 **13 MB**。
- 动态维度完整保留在 `dimensions_json`；CSV 仍有 UTF-8 BOM。
- **没有建立 PostgreSQL/MySQL/SQL Server 连接，没有执行数据库写入**。真正 SQL 入库耗时、索引维护代价必须在企业目标环境压测。

## 与原计算内核的回归

V19 与 V20 在相同的虚构「75% 材料 + 25% 收入分支 → 合并」规则、相同运行参数下执行：

- `results.csv` 完全相同。
- `ledger.csv.gz` 完全相同。
- `reconciliation.csv` 完全相同。
- `source_to_pool.csv.gz` 完全相同。
- `lineage_links.csv.gz` 完全相同。

以上五份文件逐一 SHA-256 对比一致。V20 的性能目标不是让既有核心计算更快，而是避免多场景/多版本场景中无管理的磁盘线性堆积，以及降低 SQL 写入的系统耦合。

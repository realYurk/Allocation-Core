# 开发者生产验收 SOP（复制即用）

## 全局原则

- Go 内核金额语义与已交付版本保持不变；每个 FC/ACT 场景及每次试算版本**从输入全量重新计算**，不做增量。
- 只有 PASS 且所有金额池对账为零的运行可入库和公布生效版本。
- SQL 业务明细要使用新 `run_id` 整体发布，事务失败不得改动已有有效版本。
- 非财务审计文件可按保留策略清理，正式结果应具备完整源输入、规则与金额证据备份。
- 不需要 Redis。单机进程/队列就够；多节点部署另做调度与数据一致性设计。

## 开发环境的自动化验收

```bash
# 只需 Python 3 标准库；计算仍由原生 Go 可执行程序承担
python3 acceptance.py --mode all --workspace ./acceptance_runs
# 包括：4 个规则、14 场景 × 2 版本、SQLite 事务回滚、阶段恢复、容量拒绝、HTTP 并发+重启

python3 acceptance.py --mode million --workspace ./acceptance_runs --timeout 600
# 120 万终端行：核对每行求和与逐池守恒，记录执行时长和磁盘消耗

python3 -m unittest discover -s tests -p 'test_db_source_fingerprint.py' -v
```

每次生成独立 `session_*` 目录及 `acceptance_report.json`。切勿将这些大批量临时试算结果打进最终生产程序包。

## 真实生产环境的准入标准（上线检查单）

1. **规则覆盖率**：除通用案例外，选择你们最复杂的真实 FC 规则、零分母、负数金额、跨期间、双/三驱动、分叉汇合、数据稀疏性，全量验算与可信财务基准逐项一致。
2. **容量**：估算 `pool × 目标 × 路径` 的最坏结果行数；实测 `results.csv`、压缩 ledger、检查点、输入快照、数据库写入和事务日志的峰值占用。独立磁盘卷及 OS/容器配额是硬性要求。
3. **性能 SLO**：提前由业务明确合理目标，如 14 场景的总执行窗口与单任务最大耗时；在**和生产相同**的 CPU/IO/数据库环境下逐档测 12 万、120 万、1200 万级（按资源预算），记录 P50/P95，多次复测不取单次最快值。
4. **并发**：从 1、2、4 个真实场景任务逐步提升，观察吞吐、磁盘读写、内存峰值、队列等待和数据库锁。脚本中的 28 次小规模演示只验证隔离/并发逻辑，不代表大型数据压力。
5. **故障恢复**：阶段完成后的 `--resume` 已自动核验；“执行中断电/kill、磁盘满、服务被杀后重启”必须在隔离环境进行故障注入并校验旧有效版本不变。
6. **数据库发布**：详见 `REAL_DB_ACCEPTANCE_CN.md`。先小规模，后百万/千万导入；实测 WAL/事务日志、锁、索引、复制时间，设置查询兼容和回滚预案。
7. **监控审计**：保存输入 SHA、规则 SHA、计算摘要、守恒表、结果 SHA、证据 manifest、应用日志、任务状态、DB 提交/回滚标识和测试报告；必要时进行血缘反查抽样。
8. **安全**：HTTP 默认本机；生产跨机要网关/TLS/身份鉴别、最小权限与禁止任意路径读取。落地独立文件权限和备份策略。

## 已知产品边界

- 无跨节点分布式强事务和统一共享文件锁协议；不能让多实例随意并发写同一个本地工作目录。
- 容量策略是**软预算**，不替代硬配额及失败后处理。
- 目前实时压测环境仅 Linux x64 容器；跨平台二进制已提供但目标系统需要单独验收。
- 真实 PostgreSQL、SQL Server、Oracle、MySQL 性能没有在本次环境实测；后两者没有同等级的可运行批量发布适配器。
- 自动化的恢复验证复用已完成阶段，没有模拟意外断电/阶段内部 kill。

## 关于代码身份

正式产品名为 Allocation Core。发布哈希/构建追踪在发行清单，不在计算核心帮助消息里混放多个产品版号。`allocation-ir/2.0` 和 `/v1/jobs` 是不可随意删除的兼容协议标识，FC 的版本是业务维度。

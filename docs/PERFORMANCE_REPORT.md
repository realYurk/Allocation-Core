## 1. 吞吐量（原始数据）

规模定义：**结果行数 = 成本池数 × 目标 SKU 数**。三个档位分别对应百万、千万、亿级。

| 档位 | 成本池 | 目标 SKU | 结果行数 | 耗时 | 吞吐 |
|---|---|---|---|---|---|
| 百万级 | 1,200 | 1,000 | **1,200,000** | 4.43 s | 27.1 万行/s |
| 千万级 | 1,200 | 10,000 | **12,000,000** | 43.45 s | 27.6 万行/s |
| 亿级 | 12,000 | 10,000 | **120,000,000** | 432.6 s（7.2 分钟） | 27.7 万行/s |

**关键观察**：三档吞吐几乎恒定在 **27–28 万行/秒**，说明引擎是线性扩展的——行数翻 10 倍，耗时也约翻 10 倍，没有出现超线性退化或内存爆炸。

> 吞吐随 `--workers` 提升。上表为 `--workers 4`；在 12 线程机器上可进一步调高。`--disk-partitions` 模式下会以更多磁盘 IO 换取更低内存占用（见第 4 节）。

`--evidence-gzip` 开启流式 gzip 压缩，流水与血缘体积大幅下降。

| 档位 | 结果行数 | results.csv | ledger.csv.gz | 总输出 |
|---|---|---|---|---|
| 百万级 | 120 万 | ~140 MB | — | 147 MB |
| 千万级 | 1,200 万 | ~1.4 GB | — | 1.47 GB |
| 亿级 | 1.2 亿 | 11.9 GB | 2.79 GB | 14.7 GB |

**说明**：

- `results.csv` 是最终分摊结果，未压缩（便于直接消费）；`ledger.csv.gz` 是完整流水，gzip 后从数十 GB 压到 2.79 GB（亿级）。
- 若要进一步压缩 `results.csv`，可在消费端自行 gzip；引擎把"结果"和"凭证"分开，凭证默认压缩。

## 3. 金额守恒一致性（准确性）

这是引擎最核心的保证，也是本次压测重点验证的对象。每次运行后，脚本都会做三重独立校验：

### 3.1 顶层守恒

`run_summary.json` 中 `input_amount` 必须严格等于 `output_amount`。

| 档位 | 输入总额 | 输出总额 | 是否守恒 |
|---|---|---|---|
| 百万级 | 6,000,000.00 | 6,000,000.00 | ✓ |
| 千万级 | 6,000,000.00 | 6,000,000.00 | ✓ |
| 亿级 | 60,000,000.00 | 60,000,000.00 | ✓ |

### 3.2 逐池对账

`reconciliation.csv` 对每个成本池单独核算，`delta` 列必须全为 0。

| 档位 | 池数 | 对账结果 |
|---|---|---|
| 百万级 | 1,200 | 全部 delta=0 ✓ |
| 千万级 | 1,200 | 全部 delta=0 ✓ |
| 亿级 | 12,000 | 全部 delta=0 ✓ |

### 3.3 结果行合计

脚本逐行累加 `results.csv` 的 `amount` 列，总和必须等于输入总额（亿级为 6,000 万，逐行累加 1.2 亿行验证）。

**结论**：从 120 万行到 1.2 亿行，金额一分不差。守恒不是"接近"，是精确相等。

## 4. 精度与边界（准确性细节）

用 `bench/precision_probe.py` 做了 7 项边界验证，全部通过：

| 验证项 | 结果 |
|---|---|
| 最大余数法：1 分钱分 3 份 | 0.34 / 0.33 / 0.33，余数给最大者，确定性 ✓ |
| 精度 0（整数元） | 通过 ✓ |
| 精度 6（微元，unit=1e6） | `123.456789` 精确解析分摊 ✓ |
| 大额 9 万亿 + 0.99 | 接近 int64 上限仍精确守恒 ✓ |
| 负权重默认拒绝 | 未显式允许时被拒绝（exit 1）✓ |
| 跨池守恒（3 科目 × 4 SKU） | 每池独立守恒 ✓ |
| 确定性（同输入两次运行） | results.csv SHA-256 完全一致 ✓ |

**引擎的精度机制**：

- 金额以 `int64` 定点数存储，默认精度 2（即"分"），可配置 0–6。
- 分摊时用 `math/big` 做 `金额 × 权重 / 权重和`，只有最终结果才落回 `int64`，因此中间过程不丢精度、不溢出。
- 不可整除的余数用**最大余数法**分配，规则确定（余数大者优先，并列按标识排序），保证同一输入永远得到同一输出——这对审计和复现至关重要。

## 5. 灵活性（这个组件能做什么）

压测之外，引擎在功能层面覆盖了这些真实业务形态（均有示例或测试）：

| 能力 | 说明 | 示例 |
|---|---|---|
| **单因子分摊** | 一个驱动分到底 | `cosmetics` |
| **多因子分摊** | 同一阶段叠加多个驱动（销量 + 用料） | `dual_driver`、`triple_driver` |
| **两阶段 DAG** | 先分到系列、再分到商品 | `manufacturing` |
| **分叉合并** | 中间结果分叉再合并 | `split_merge` |
| **有符号权重** | 负权重冲销（需显式允许） | `negative_driver_policy` |
| **维度层级** | 通过 `hierarchies` 定义父子关系自动展开 | `hierarchies` 字段 |
| **批量** | 一次跑多个规则 | `alloc batch` |
| **持久工作区** | 规则发布、版本 diff、任务历史、重试 | `alloc workspace` |
| **归档生命周期** | 结果归档、校验、恢复、清理 | `alloc vault` |
| **血缘追踪** | 任一行结果追溯到来源池与权重 | `alloc trace` / `trace-index` |
| **容量准入** | 提交前估算规模，超预算拒绝 | `alloc capacity` |
| **HTTP 服务** | 长驻多租户调用 | `alloc serve` |

一句话概括灵活性：**分摊拓扑（几步、每步按什么分、分给谁、守恒粒度）全部由一份 JSON 声明**，改规则不需要改代码、不需要重新编译。

## 6. 已知边界与诚实声明

这些是真实存在的边界，接入前需要知道：

1. **无增量分摊**：每次都从原始数据全量重算。好处是结果永远可复现、不会累积误差；代价是大数据量时每次都要算全量（可用 `--checkpoint-dir` + `--resume` 复用已完成阶段）。
2. **`results.csv` 未压缩**：亿级结果 11.9 GB，消费端要注意磁盘和带宽。凭证（ledger）已默认 gzip。
3. **内存与磁盘的权衡**：内存模式下千万/亿级会占用较大内存；`--disk-partitions` 用 IO 换内存。具体峰值内存见下节历史数据。
4. **容量准入是软预算**：估算输出规模并拒绝超限任务，但不是 OS 级磁盘配额，生产环境仍需独立磁盘卷 + 硬配额 + 监控。
5. **跨币种不能混加**：`currency` 必须进 `immutable_dimensions`，不同币种分开守恒。
6. **本报告为单机合成数据**：真实生产吞吐受磁盘 IO、并发、数据分布影响，需在目标环境实测。

## 7. 历史性能基线（跨版本）

引擎内核各版本在 `core/bench/` 留存了历史指标（Linux 容器，`/usr/bin/time -v` 实测）：

| 版本 | 场景 | 结果行 | 峰值内存 | 备注 |
|---|---|---|---|---|
| V10 | 单阶段 | 120 万 | 28–42 MB | workers 1→4 |
| V12 | 两阶段 | 120 万 | 45 MB | 含检查点，复用后 8.8 MB |
| V13 | 磁盘索引 | 120 万 | 28 MB（磁盘）/ 46 MB（内存） | 磁盘索引用 IO 换内存 |

对比本次 Windows 实测（亿级 432s / 守恒精确），引擎的**守恒与精度特性在各版本间保持不变**（`formula_behavior: unchanged`，见 `RELEASE_IDENTITY.json`），版本演进集中在证据压缩、索引、归档、容量准入等外围能力，未触碰金额算法。

## 8. 结论

| 维度 | 结论 |
|---|---|
| **性能** | 27–28 万行/秒，线性扩展，亿级 7 分钟跑完 |
| **一致性** | 从 120 万到 1.2 亿行，金额精确守恒，逐池对账全 0 |
| **精度** | int64 定点 + big 中间量，9 万亿大额、6 位小数均无误差 |
| **确定性** | 同输入同输出（SHA 一致），可审计可复现 |
| **灵活性** | 拓扑/驱动/守恒粒度全声明式，改规则不改代码 |

# Allocation Core V17｜性能、审计与优化评估

## 结论

**有优化空间，但现阶段最值得突破的是输出 I/O、计算证据存储和高频追溯，而不是简单增加计算线程。** 本版保持分摊数学语义、分支合并和规则协议不变，把可选的无损证据压缩与快速磁盘血缘索引做成独立后端能力。

## 用户提供的第三方 Windows 压测（不是本次复测）

测试机 i5-12490F、6 核 12 线程、16 GB 内存。使用现有 `go-core/0.16.0`：

| 终端结果行 | 运行时间 | 峰值内存 |
|---:|---:|---:|
| 24 万 | 0.93 秒 | 39 MB |
| 120 万 | 3.60 秒 | 48 MB |
| 600 万 | 16.4 秒 | 135 MB |
| **1,200 万** | **31.8 秒** | **250 MB** |

这份外部报告还提供了 1/4/8 线程、多因子、负金额和最大余数验证。我们没有拿到报告运行时的完整原始计算文件，也没有在当前会话复现 1200 万行；因此成绩应标注为用户提供的独立测试，不应拿来与执行范围不同的其他生产系统直接计算加速倍数。

报告指出 1200 万行的 `results.csv` 约 1.2 GB、`ledger.csv` 约 3.2 GB。它恰好暴露了新的关键瓶颈：**审计和结果存储**。

## V17 当前环境实测：120 万终端结果对应的完整审计集

在已有的同一批 V16 合成输出上评估新功能（不重新计算分摊金额）：

| 测试项目 | 本轮结果 | 说明 |
|---|---:|---|
| 原始审计文件 | 441,968,846 字节 | 约 421.5 MiB |
| V17 完整无损 ZIP | 46,280,681 字节 | 约 44.1 MiB |
| **空间节省** | **89.53%** | 原 CSV 一字节未删 |
| 索引增量存储 | 约 28.9 MB | 64 分片/文件的二进制偏移索引 |
| 无索引单行血缘查询 | 2.733 秒 | 全表顺序扫描 |
| 构建索引 | 1.22 秒 | 一次性操作 |
| 有索引单行血缘查询 | **0.0037 秒** | 仅定位相关分片 |
| 完整索引 SHA-256 验证 | 0.25 秒 | 对原 CSV 与索引分片哈希 |
| 完整无损打包 | 1.79 秒 | 额外后处理开销 |
| 完整归档 SHA-256 验证 | 约 1.0 秒 | 每个文件逐字节校验 |

## 技术新增

1. `trace-index OUTPUT_DIR`：为 `ledger.csv`、`source_to_pool.csv`、`lineage_links.csv` 建立可重建的持久化反向索引。原 CSV 不变。构建过程中先写临时目录，成功后原子发布。
2. `trace-index-verify OUTPUT_DIR`：对原始证据及所有索引分片做 SHA-256；读取血缘时，如果原始文件大小或时间发生变化，拒绝使用过期索引。每次查询的索引分片也要先校验 SHA-256。
3. `audit-pack OUTPUT_DIR AUDIT.zip`：无损归档完整计算输出，包含 SHA-256 manifest，不删除原始文件。
4. `audit-verify AUDIT.zip`：对压缩内容逐字节校验，包括 ZIP 数据损坏的拒绝。
5. `audit-extract AUDIT.zip TARGET_DIR`：只恢复到全新目录，不覆盖已有文件；恢复后的 CSV 与原始 CSV 按字节相同。

## 质量验证

Go `go test ./...`、`go test -race ./...`、`go vet ./...` 均通过；新增测试覆盖索引/全量扫描等价、索引过期拒绝、索引分片损坏拒绝、压缩恢复逐字节一致、篡改 ZIP 拒绝。Windows x64/ARM64、Linux AMD64、macOS ARM64 已交叉编译；目标 Windows 电脑仍需验收。

## 诚实的边界

- 还没实现**计算时直接压缩/列式写出**，这是未来真正可能缩短 1200 万行全量运行时间的方向，需要保护检查点一致性和差分结果。
- 这个 ZIP 是完整性校验，不是数字签名或不可篡改凭证；能同时修改原文件和 manifest 的恶意操作仍需要不可变存储或数字签名来防范。
- 血缘是因果路径，不意味着已计算到每个原始凭证的一分钱归因。
- 索引本身额外占空间，数据改变时需重新构建；极端高扇入的路径检索仍需容量控制。
- 没有把客户真实生产场景与合成数据混为一谈，也没有声称 V17 的分摊算法比 V16 又快了多少。

## 下一步工程方向（建议）

**V18：流式压缩证据输出 + 无损列式存储试验 + 10M/100M 不同数据倾斜基准 + 定量比较计算/写盘耗时。** 任何格式优化必须做到：校验逐金额池守恒、确认跨多线程确定性、能够导出与当前 `ledger.csv` 完全等价的证据。为适配现有系统保留 CSV 默认模式。

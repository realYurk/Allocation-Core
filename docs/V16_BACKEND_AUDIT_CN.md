# Allocation Core V16 · 严格后端评审

## 产品定位

它是一套**规则驱动、多维度、多阶段、可验证的公共费用分摊计算内核**。接入企业 ERP、财务平台、计划系统或者独立数据管道时，后端规则和运行协议应该保持不变；前端属于可替换的用户交互层。

## 优先级审计

| 级别 | V15 发现的问题 | V16 处理 | 余下限制 |
|---|---|---|---|
| P0 | 同一坐标的多路输出经过自动归并后，只保留一条 `row_id`，其他上游无法继续反查 | 写出 `lineage_links.csv`，保留被折叠的 `parent -> child` 关系；MERGE 显式记录支路到汇总行 | 这些边表示因果归属，**不是金额分摊比例**；精确金额仍看 ledger 与成员证据 |
| P0 | 多份金额文件有相同 `row_id`，上游证据可能碰撞 | 输入行标识同时带来源数据集、原行号和顺序 | 外部对接应持久保存原始业务单据 ID 的映射 |
| P0 | CSV 重复列名被后一个覆盖 | 统一字段校验，拒绝重复/空列名；覆盖内存、磁盘 Driver 索引、Doctor | 用户仍需为各列标明单位与有效期间 |
| P1 | JSON 后续拼接内容未强制拒绝 | 每份规则必须恰好包含一个 JSON 对象 | 规则内容的更细粒度财务语义应继续丰富 |
| P1 | 能看到分摊结果，但难从某行回溯完整多路径 | 新增 `trace-first` / `trace`，从最终输出逐段逆向读取合并边、驱动明细和金额来源 | 大规模高频追踪应建立持久索引，当前是顺序文件扫描 |
| P1 | 断点恢复必须能带回血缘文件 | 升级检查点格式并重放血缘证据，新增恢复一致性测试 | **旧 V12–V15 检查点不兼容**；应新建检查点目录 |

## 重要的领域语义审计结论

- **多因子不是多步骤**：一个节点的分配份额总和应为 100%；多步骤节点之间边的份额也必须独立满足 100%。
- **允许的守恒边界**必须由规则指定的维度组合决定。不能只看公司合计为零就宣称规则正确。
- **维度 SOURCE / TOTAL / AS_IS 约束**已有编译期保护；仍要继续补“不合法驱动粒度”“重复目标”“数据空洞”等语义校验。
- **负金额与负 Driver 不应混为一谈**：负费用允许带符号守恒；负 Driver 只有显式允许且总分母为正才执行。更多业务策略需要明确配置，不宜写死。
- **同一 SKU 在两条 Driver 下可有两条 ledger**，这不是重复入账；最终财务报表应按指定维度归并以便理解。
- **货币处理：** 实际内核用 int64 最小计量单位与确定性余数分配，精度 0–6 位；这规避普通浮点尾差，但总金额容量、币种、会计精度、舍入政策仍必须在企业接入时审核。

## 真实性能测试（当前 Linux amd64，Go 1.23.2，合成数据）

| 方案 | 最终记录 | 两阶段金额池 | 耗时 | 峰值常驻内存 |
|---|---:|---:|---:|---:|
| V15 原版 | 1,200,000 | 3,600 | 5.52 秒 | 约 39 MB |
| V16 加强血缘/校验版 | 1,200,000 | 3,600 | 5.33 秒 | 约 45 MB |

场景：100 科目、12 期间、1000 商品，费用 → 系列 → 商品，4 个工作线程、16 磁盘分区。`results.csv`、`ledger.csv`、`reconciliation.csv` 在两版间 SHA-256 完全一致。V16 新增 `lineage_links.csv` 及来源 ID 命名空间，故 `source_to_pool.csv` 不会与旧版本逐字节一致。耗时差异只是单次运行波动，不应解读成确定的性能提升。多阶段数据倾斜、海量多因子和 10M+ Driver 仍需专项压力测试。

## 诚实的能力边界与 V17 优先路线

**已运行的能力：** 动态维度、源金额池、目标筛选、多因子、DAG 多阶段、守恒、整数定额分配、多线程、磁盘分区、Driver 外部索引、任务快照/检查点、HTTP、财务对比输出和合并血缘边。

**下一批 P0：**
1. **财务语义编译器 / 策略引擎**：将“缺失驱动怎么办”“分母为零”“负 Driver/费用”“跨期间/跨币种”“范围筛选后余款如何处理”做成显式规则，拒绝静默的默认行为。
2. **真正的可检索血缘索引**：针对大量结果的按 SKU、期间、科目逆向/正向追踪；持久化 DAG 的节点、连接与可核对的金额归属。
3. **性质测试与差分测试**：随机 DAG、随机负数/零权重、不同 worker/partition 数、内存与磁盘/检查点/缓存模式的对比；避免只靠四个演示样例。
4. **任务取消与失败隔离**：上下文取消、响应超时、资源配额、幂等写回，避免生产任务无限占 CPU/磁盘。
5. **大数据性能**：外部血缘索引、热点金额池分裂、增量 Driver 索引、文件批量写出、profiling 有依据地减少分配。**不建议此时为 Java/Python 再单独写一套计算内核**，除非有明确原生嵌入/性能要求和可用的全套跨语言黄金测试。

审批流程不在当前产品目标内；前端可以保持简洁，不应变成计算语义的唯一来源。

# 不懂代码也能理解：怎样把 Allocation Core 接入任何公司？

## 1. 先理解一句话

**这是一台单独的分摊计算发动机，不是必须替换你公司系统的软件。**

你现有系统继续管理科目、期间、商品、财务数据和前端页面；计算核心只负责把你交给它的金额和 Driver，按照规则**从头算一遍**，并返回结果、对账和来龙去脉。

可以想象一家餐馆：**现有系统是点菜和收银台，Allocation Core 是后厨**。不需要把收银台重做成后厨，也不需要把后厨用 Java、Python 再重写一遍。

## 2. 你应该下载什么？

| 你的情况 | 最省心的方案 | 程序在项目里长什么样 |
|---|---|---|
| 一台 Windows 电脑，偶尔计算 | 直接调用独立 EXE | 一个 `alloc_windows_amd64.exe` 文件 + 规则/data |
| 公司已有 Java/Spring Boot 系统 | **推荐：HTTP 服务 + Java 小 JAR** | 后台运行 Go EXE；Java 只负责 HTTP 调用 |
| 公司已有 Python/Django/FastAPI | **推荐：HTTP 服务 + Python 客户端** | 后台 Go EXE；Python 负责请求、下载文件 |
| Excel/VBA 或既有模型平台 | 导出 CSV、调用 EXE 或内部 HTTP、再导入 | 原系统界面和计算模型不用替换 |
| 企业只允许单进程、不能起服务 | EXE 命令行模式 | 系统通过子进程调用，每次运行独立 |
| 需要几千万行长期查询 | SQL/分析库保留必要结果，审计归档另存 | 结果写入由你公司自己的数据库服务完成 |

**JAR 不包含分摊引擎。** 它只是打包的 Java 接口。如果你强制要求一个纯 JAR、完全不部署 Go 程序，目前还不支持，需要另立跨语言重写与一致性验收项目。

## 3. 一个新公司只需要准备哪些东西？

用下面的例子理解：

- **费用金额表**：每个月每个科目要分多少钱。例如 2026-01、能源费、1200 元。
- **驱动数据表**：按工时、销量、收入等依据分摊。可以有一套或多套。
- **维度字段**：期间、科目、工厂、品牌、商品、门店等。不同公司可以不一样。
- **规则文件**：哪个范围的钱能合在一起、不能跨什么范围、按什么 Driver、多步骤怎么连接。
- **结果接收方式**：生成 CSV、写 SQL、回传 API 或导回既有模型系统。

若你只想先跑起来，直接用 `core/examples/manufacturing/` 中的**完全虚构**数据。接入真实企业时，请由熟悉业务的实施人员核对字段与保密要求。

## 4. 最重要的全量重算流程

```text
第1步 业务人员确认场景（FC 10+2 / ACT）和测算版本
  ↓
第2步 从现有系统/SQL 取出本次完整金额、完整 Driver、规则版本
  ↓
第3步 冻结这次输入，记录哈希；绝不拿上次结果当成本次来源
  ↓
第4步 调用同一台 Allocation Core 全量计算
  ↓
第5步 全部金额池 PASS、来源总额与最终总额一致才继续
  ↓
第6步 如需入库：先写新的 run_id，核对行数和金额，再切换当前生效版本
  ↓
第7步 原始快照 + 规则 + 完整证据保留到按策略管理的归档里
```

**不要直接删除老版本，然后边算边写正式表。** 失败时老版本仍应继续有效。

## 5. 真实演示：1,200 元改成 2,400 元

这个包里有一套可以独立运行的 SQLite 示例：

```bash
python integration/python/sqlite_full_run.py --workspace ./demo_workspace --reset-demo
```

输出（商品 A/B/C/D）：`100 / 300 / 400 / 400`。

之后运行：

```bash
python integration/python/sqlite_full_run.py --workspace ./demo_workspace --amount 2400.00
```

输出：`200 / 600 / 800 / 800`。

数据库内保存两次独立运行，只有 `allocation_active` 指向第二次结果。第一次的正式金额没有被直接修改。

**这是教学规模的 SQLite 适配器，不是用于千万行企业 SQL 的高性能导入器。** 大规模场景应使用 PostgreSQL COPY / SQL Server SqlBulkCopy 等批量工具。

## 6. Redis 要不要？

**第一阶段完全不需要。**

你现在核心使用的是单实例 Go 程序，加上一个现有 SQL 数据库或目录存储，就能支持全量计算。Redis **不会让分摊数学公式更快**；它主要可能用于以后多节点的队列、锁、节流或暂存状态。但在你没打算做分布式多节点任务调度时，加 Redis 是额外部署成本和数据一致性风险。

## 7. 14 个场景和很多测算版本怎么处理？

- 场景：`FC0+12`, `FC1+11`, …, `FC12+0`, `ACT`，使用公司自己的命名规则；不写死成十四个特殊分支。
- 每次计算：一个**新的唯一 run_id**；允许同场景同业务版本反复完整重算。
- 当前有效结果：数据库只保存一个指针 `scenario + business_version -> run_id`，可以切换。
- 试算：可以按保留天数、保留最近 N 次清理，需可预览且避免误删。
- 正式结果：保留必要明细及完整证据；中间明细、血缘放压缩 Vault，不必全塞数据库。

## 8. 你怎么验收一家公司接入成功？

不仅要求界面显示 0 差额，还要求：

1. 双因子、多因子、多步骤、分叉合并示例结果准确。
2. 每个保留维度/金额池的守恒检查 `PASS`。
3. 换线程数输出金额一致；每次运行可从规则/源数据快照重现。
4. SQL 写入失败能回滚，当前有效版本**不会被破坏**。
5. 业务人员能够按科目、期间、SKU 查询，并从原始 run_id 找到完整证据。
6. 产品核心程序本身不需要为新公司新增一个行业 `if` 判断。

**推荐先用独立服务嵌入现有系统，不重造你已经验证很快的 Go 内核。**

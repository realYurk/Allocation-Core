# V19 工程变更与可复验性能测试

## 已实现的能力

- 读取 V18 流式 gzip 审计文件，**一次性建立可随机定位的 gzip 分块副本**（每块至多 512 行或约 1 MiB）。
- 每个分块独立 gzip 成员，按行关键字建立 64 分片 SHA-256 前缀索引；随机查询仅解压命中的分块，不先恢复全部明文证据。
- `trace-first/trace` 自动识别 V19 索引，复用完整 DAG 向上追溯逻辑；`trace-pack-verify` 全量校验原始压缩文件、分块文件、目录和索引散列。
- 可删除 `trace_packed_v19/` 重新生成，不影响原始计算产物；建立过程原子发布，失败不发布半成品索引。
- 同时保留原有 V17 明文 CSV `trace-index` 和 V18 `evidence-expand` 命令，向后兼容。

## 120 万条合成业务结果实测（当前 Linux 容器，非 Windows 压测复刻）

来源数据：100 费用科目 × 12 个月 × 1000 个 SKU，两阶段工厂系列分摊，4 工作线程，16 磁盘分区，直接输出 gzip 证据。计时口径均为**单次程序进程墙钟耗时**。

| 操作 | 耗时 | 进程峰值 RSS |
| --- | ---: | ---: |
| V19 计算并输出 V18 gzip 证据 | 5.28 秒 | 48 MiB 左右 |
| 基于压缩审计建立 V19 索引（包括前置校验） | 5.90 秒 | 47 MiB 左右 |
| 使用压缩索引追溯一条 SKU 完整上游路径 | 小于 0.01 秒 | 约 10 MiB |
| 完整验证原始审计和 V19 索引 | 0.81 秒 | 约 11 MiB |
| 旧流程恢复完整明文 CSV | 2.93 秒 | 约 11 MiB |
| 无索引、明文顺序扫描查询相同 SKU | 2.96 秒 | 约 13 MiB |

- 完整生成 1,200,000 条 `results.csv` 明细，索引目录约 **56 MiB**；原 `ledger.csv.gz` 约 23 MiB。**这是额外空间，不是节省空间。**
- 两种查询方式的 JSON 链路完全一致（来源 ID、边、金额、规则与分母）。
- 自动化测试覆盖了双因子、三因子、分叉合并、两步骤、故意破坏 gzip 或索引后的安全失败。
- 查得快的原因是随机访问压缩数据块。当前是**可选二级副本**，不是直接随机访问单条不可分块的传统 `.gz` 文件，也不是 V18 计算时原地建立的最终统一索引。

## 严格边界与后续优化

1. 大型 ledger 的索引首次构建仍需完整校验与解压读取；不能认为构建时间为零。
2. 旧 gzip 与新分块并存，产生二次存储成本。下一步应研究计算过程中直接输出原生可随机访问的分块证据、并以归档策略替代原 gzip 副本，而非默默删除法定审计信息。
3. 单次查询仅校验命中块的 gzip 校验和与涉及的索引分片；对整个索引和原始文件强完整性检查需显式运行 `trace-pack-verify`。防止显式元数据改动使用尺寸与时间戳检查，但这不是防恶意篡改的签名机制。
4. 性能测试为合成数据，不能代表用户自己的分摊规则、极端高扇入 DAG 或实际生产硬件。
5. 为了财务正确性，所有计算公式、尾差策略、分区与驱动解释逻辑均保持 V18；本版仅增加查询路径。

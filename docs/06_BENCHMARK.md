# V14 缓存与一致性实测（2026-10-23）

测试环境：当前 Linux x86-64 容器，Go 构建后的独立原生程序，4 workers，8 disk partitions，合成虚构数据。计时为 `/usr/bin/time` 墙钟时间，RSS 为最大常驻集（KB）。Windows 现场速度未实测。

| 场景 | 结果行 | 金额池 | 冷缓存 | 热缓存 | 峰值内存 |
|---|---:|---:|---:|---:|---:|
| 24科目×12期间×500商品，2阶段 | 144,000 | 864 | 0.80 秒 | 0.77 秒 | ~17 / 16 MB |
| 20个期间×15,000商品，单阶段，Driver 300,000行 | 300,000 | 20 | **3.01 秒** | **1.20 秒** | ~101 / 101 MB |

第二组冷缓存→热缓存速度改善约 **2.5 倍**，它体现重复索引构建被省去；**不是所有分摊业务都会加速 2.5 倍**。对第一组而言，Driver 行数较小，索引缓存对整个计算的收益有限。

两组冷/热结果都分别检查四个输出文件：`results.csv`、`ledger.csv`、`reconciliation.csv`、`source_to_pool.csv`，对应 SHA-256 **逐字节相同**。第二组金额总计 **600,000.00 → 600,000.00**，20 个金额池全部守恒；第一组 633,600.00 → 633,600.00，864 组守恒。

另外实际启动 V14 HTTP 服务，提交两阶段任务得到 PASS，关闭并重新启动服务，同一 Job ID 仍可查询并读取中文 `results.csv`。测试中每次提交会冻结原规则和驱动 CSV，历史任务有对应的输入哈希。

严格边界：并未对 Windows 客户机、百万级多分支 DAG、多亿行 Driver、断电中途及多个服务实例共享工作区进行性能/可靠性认证。

# V21.1 给非开发人员看的说明：为什么又出修订版？

## 这次没有改变你已经跑得很快的分摊内核

这次处理的是“怎么交给其他公司、其他项目安全地使用”：Java 能下载所有凭证；文件下载中断不覆盖旧文件；正式运行之前先估算要写多少数据；正式需要重演时另存一份原始输入。

**V20 内核原样不动。全部 14 个 FC/ACT 场景及多个版本仍然各自从源金额和 Driver 完整重算。** 没有使用增量计算，也不需要 Redis。

## 和你实际工作有什么关系？

例如一次 FC 10+2 试算，计算前先估算“费用池 × 每池有效目标 SKU × 驱动路径”，确认输出目录是否够大。执行后，结果和审计证据正常生成。正式版本使用 V20 Vault 压缩归档结果，**另存规则、金额和 Driver 快照**；这样以后才有条件原样重演。

过去只保存 Vault，相当于保存“答案和解题过程的证据”；补充输入快照则是保存“当时的题目”。两者职责不同。

## 软件怎么接入 Java / Python？

- **Java**：将 `integration/java/allocation-client-java8.jar` 加入现有 Spring Boot 项目。它只是 HTTP 调用工具，不是另一套计算引擎。
- **Python**：复制 `integration/python/http_client.py` 到原工程，用其提交任务和下载证据。
- **其他工程**：调用相同的 HTTP API，或者启动 Windows EXE 作为子进程。
- **SQL**：系统取原始数据给分摊引擎；计算完成后按原业务表结构批量导入结果。完整 ledger 保留压缩证据，不强求全部入 SQL。

## V21.1 到底修了什么？

1. Java JAR 原来只能下载 4 种文件，这次对齐服务端全部 **10 种**，包括 `.gz` 压缩审计文件。
2. Java/Python 下载失败不会直接把你本地已有的好文件覆盖掉。
3. 增加**运行前容量预算工具**，明显过大的任务提前拒绝。注意它不是自动精准预测。
4. 增加单独的**输入快照工具**，保留未来从头重演的规则和原始数据。
5. 给软件建立一个清晰的发行身份：**Integration V21.1.0**。旧计算核心里的老版本文字保留原样，避免破坏其 SHA-256 冻结。

## 如何验证？

- 不需要开发环境：解压后仍可运行 `core/01_Windows_Run_Two_Stage.bat` 体验原始计算。
- 有 Python 的开发电脑：运行 `python integration/tools/release_info.py` 核对 156 个文件完整性。
- 开发人员参考 `docs/05_V21_1_Audit_Fixes_CN.md` 运行容量预算工具、Java/Python 实际 HTTP 测试与输入快照。

**不要把预估 18 亿行理解为你公司的真实结果。** 这个只是第三方审计场景的极端规划示例，具体以每个真实金额池的有效目标集合和驱动配置为准。

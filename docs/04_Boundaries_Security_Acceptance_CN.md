# 产品边界、Redis 是否必要、长期稳定性与上线验收

## 1. 我们提供什么，不提供什么

| 模块 | 交付方式 | 责任归属 |
|---|---|---|
| 分摊计算逻辑 | **锁定的 V20 Go 核心** | Allocation Core |
| 多步骤 DAG、多驱动、守恒、精度、血缘 | 引擎自带 | Allocation Core |
| HTTP/CLI 接口 | 引擎自带 | Allocation Core |
| Java 调用 | 轻量 JAR + 源码 | 集成套件（HTTP SDK） |
| Python 调用 | 标准库文件 + 示例 | 集成套件（HTTP SDK） |
| 源数据库查询/字段映射 | 可复用示例 + 公司配置 | **接入项目** |
| SQL 批量导入/表结构 | SQLite 已验证；其他方言模板 | **接入项目 + DBA** |
| 前端业务页面 | 可选的离线示例 | **宿主项目 UI** |
| Redis/消息队列/数据库调度 | 默认无需 | 宿主项目根据规模决定 |
| 企业级 TLS/RBAC/多租户/高可用 | 目前未内建 | 企业网关、IAM、部署系统 |
| 独立原生 JAR 计算引擎 | **不提供** | 需另行设计并验证 |
| 增量复算/改变旧结果 | **禁止，本版不提供** | 每次重新完整计算 |
| 审批 | 不做 | 用户明确不需要 |

## 2. Redis：在什么情况下才需要？

**单机、单实例、有限并发：不需要 Redis。**

- 可以用数据库保存场景/任务与生效版本。
- 一个 Go Core 服务内已有受控并发队列和文件任务状态。
- 依赖 Redis 不会自动提高金额计算吞吐，也不能替代守恒校验。

以后若需要多实例水平扩展，可讨论数据库队列、Kafka、RabbitMQ、Redis Stream 等，但先要解决运行目录隔离、任务幂等与租户权限。**不要预先为尚不存在的分布式需求加入 Redis。**

## 3. SQL 写入的发布协议

1. **新的 `run_id`**：生成不可复用的唯一运行号。
2. 冻结规则/金额/Driver 完整输入快照与 SHA。
3. 全量计算到隔离的新输出目录；运行成功并守恒 PASS。
4. 装入 staging，验证行数、DECIMAL 金额总和、run_id、唯一键、非空等。
5. 单事务写入新 `run_id` 的结果，并只修改当前生效版本指针。
6. 旧 `run_id` 仍能查询和还原；过期草稿根据保留政策回收，正式版本受保护。

任何时候，不要将“上次的结果数据”作为本次新的输入来计算（除非它本来就是*同一次运行 DAG 中上一个阶段*，那是多步业务规则）。

## 4. 真正上线前，应该如何严格测试？

**正确性：** 验证不同 SKU、不同维度、零分母、负金额、多币种、重复表头、无效 Driver、多分支合并、整数尾差、不同线程结果一致；所有金额池守恒通过。

**一致性：** 针对真实场景冻结完整数据快照；重复运行产生相同输出；保存对应规则哈希和输入哈希；禁止把不同计算版本混起来入库。

**可靠性：** 验证数据库批量导入中途失败、空间不足、任务取消、网络失败、服务重启；确保没有半成品成为生效版本。

**性能：** 单独测 Core 计算耗时、完整 ledger 写盘耗时、SQL COPY/BULK 入库耗时、数据库报表查询耗时、归档存储量；不要混成一个“引擎性能”数字。

**安全：** 限定服务 `--root`、最小权限、拒绝绝对路径与穿越、API 令牌放在机密管理系统、跨机器通过 TLS 网关、限流和审计；不要将服务默认本机保护误当公网安全。

**运维：** 完整日志、运行 ID、磁盘水位监控、固定版本程序/校验和、自动备份、恢复演练、输入和输出保留周期。

## 5. 本阶段测试过什么

- V20 原始核心文件保留；`CORE_SHA256.json` 提供每一个文件的完整哈希可核对。
- `sqlite_full_run.py` 两次从源 SQL 全量重新计算并通过守恒、事务入库、切换有效版本。
- Java 8 SDK 编译成 JAR 后连接正在运行的 Go HTTP 服务，成功提交任务。
- Python 纯标准库 SDK 连接服务，成功提交、轮询 `PASS` 并下载 CSV。
- 没有可用的 PostgreSQL、MySQL、SQL Server、Oracle 服务，因此对应厂商导入语法尚未做实库验证；不能声称已完成所有数据库的生产接入。

## 6. 为什么不直接把 Go 编译成 JAR？

JAR 是 JVM 生态程序包，而 Go 构建的是本机程序。可以通过 JNI、C-ABI、GraalVM 等建立嵌入方式，但会增加平台组合、内存生命周期、诊断和升级成本。**现在已经有经过压力测试的独立 Go 内核，优先通过稳定 HTTP/CLI 协议复用它，比为了“看起来像依赖包”而重写更可靠。**

如果组织未来规定禁止运行独立 EXE/容器，那么就需要启动一个受控的 **Java 原生计算内核兼容项目**，必须通过所有金额和证据的差分测试后才能替换。当前这不是已实现能力。

# Allocation Core 组件接入

## Java / Python 进程客户端

源码包中的 `clients/python/allocation_core_client.py` 和 `clients/java/allocationcore/Client.java` 是轻量 SDK，提供检查、运行和对账；内部调用指定平台的 Core 可执行程序，不启动网页，也不实现第二套财务公式。Java 返回 UTF-8 JSON 字符串，供调用方现有 JSON 库解析；Python 返回字典。调用方需要相应平台的 Core 程序以及 Python 3.10+ 或 Java 8+ 运行环境。客户端不是不依赖本机程序的原生内核，也不是已验证的远程多租户服务。

Python：将客户端文件纳入项目，或把 `clients/python` 放入 `PYTHONPATH`：

```python
from allocation_core_client import Client

client = Client(r"C:\AllocationCore\AllocationCore.exe", timeout=300)
check = client.inspect(r"C:\jobs\rule.json")  # 检查失败抛 CoreError，报告可取 error.report
result = client.run(r"C:\jobs\rule.json", r"C:\jobs\run-001", workers=2,
                    disk_partitions=8, driver_disk_index=True)
print(result["status"], result["output_amount"])
```

Java：把 `clients/java/allocationcore/Client.java` 加入项目或自行编译成 JAR：

```java
import allocationcore.Client;
import java.nio.file.Paths;

Client client = new Client(Paths.get("C:/AllocationCore/AllocationCore.exe"), 300000);
Client.Options options = new Client.Options();
options.workers = 2;
options.diskPartitions = 8;
options.driverDiskIndex = true;
String summaryJson = client.run(Paths.get("C:/jobs/rule.json"), Paths.get("C:/jobs/run-001"), options);
```

`compare` 使用独立参考文件；返回 `DIFFERENCES` 是对账结果而非调用错误，必须检查返回状态。检查 PASS 不等于业务规则正确。超时会强制结束 Core 进程，不能把超时当作成功或已完成的断点恢复；强杀可能留下临时目录，重试前核查任务和存储状态。每次运行必须使用新的输出目录，不覆盖已有结果。敏感数据和完整错误/报告保留在调用方本机，不应放入公开日志或仓库。

Core 是 Go 源码模块，不依赖 Studio 和网页。`core` 包是对原有计算引擎的公开入口，和 EXE 使用同一套规则、算法、精度与守恒检查。UI、Windows EXE、Go 组件是不同使用方式，不需要都部署。

## Go 项目直接集成

推荐使用 `allocationcore/sdk`：它提供输入检查、运行和独立对账三个入口，不依赖 EXE 或网页。`allocationcore/core` 仍保留，已有调用无需更改。以下是最短调用，完整的可运行示例在 `examples/sdk-go`。

```go
import "allocationcore/sdk"

report, err := sdk.Inspect("rules/rule.json")
if err != nil { /* 文件或规则无法检查 */ }
if report.Status != "PASS" { /* 查看 report.Checks 中的错误，停止 */ }

result, err := sdk.Run(sdk.RunRequest{
    RulePath: "rules/rule.json",
    OutputDir: "output/run-001", // 必须是尚不存在的目录
    Workers: 2,
})
// 先检查 err，再检查 result.Status。结果在 output/run-001。
```

要节省内存，可设置 `Mode: sdk.Disk`、`DiskPartitions: 8`，可按需启用 `DriverDiskIndex`、`DriverCacheDir`、`CheckpointDir`、`Resume` 和 `EvidenceGzip`。空模式是内存，Workers 为 0 时使用 1，磁盘分区为 0 时使用 8；SDK 会拒绝内存模式中无效的磁盘参数，避免悄悄忽略。不要共享或覆盖已有输出目录。性能取决于金额池、Driver 基数、磁盘和数据分布，需在目标环境测量。

对账必须使用独立提供的参考文件：

```go
report, err := sdk.Compare(ctx, "output/run-001/results.csv", "reference.csv",
    "output/reconciliation-001", sdk.ReconciliationOptions{Precision: 2, RejectReferenceDuplicates: true})
// err == nil 也要检查 report.Status：MATCH 或 DIFFERENCES。
```

Core 的多因子结果可能在同一完整业务坐标下有多条合法明细；默认按坐标精确汇总并报告 `ActualDuplicateRows` 和 `ReferenceDuplicateRows`。上例允许实际结果重复，并要求参考侧坐标唯一；如果独立参考本身有合法明细，需要按其业务契约选择政策。`RejectActualDuplicates` 可单独阻断实际侧重复，旧的 `RejectDuplicates` 仍阻断两侧重复。必须核实重复行来源：两侧都默认汇总可能掩盖重复导入，不要用覆盖方式合并明细。

`Inspect` 的 PASS 只表示规则及输入结构、数值检查通过，不代表 Driver 覆盖或业务对账通过。`sdk.Run` 发生错误时返回的摘要状态为 `BLOCK`；调用方仍须首先检查错误，不能依赖摘要中的部分金额或计数判断成功。`sdk.Error` 可用 `errors.As` 查看 `Code`，`errors.Is` 仍可检查底层错误。对账支持 context 取消；Core 进程内分摊目前不支持中途取消，不能把 SDK 伪装成可取消任务。需要中止执行时使用现有受控工作进程模式。

将完整源码包放在本机，项目安装 Go 1.23 或更高版本。在自己的 Go 项目目录配置本地依赖，例如：

```powershell
go mod edit -require=allocationcore@v0.0.0
go mod edit -replace=allocationcore=C:/local/Allocation-Core
```

将路径替换为源码包实际解压路径。代码示例：

```go
package main

import (
    "fmt"
    "log"
    "allocationcore/core"
)

func main() {
    result, err := core.Run("rules/rule.json", "output/run-001", core.RunOptions{Workers: 2})
    if err != nil { log.Fatal(err) }
    fmt.Println(result.Status, result.InputAmount, result.OutputAmount)
}
```

规则文件和 Driver/金额数据必须符合既有 Core 契约，路径及输出目录由调用方提供。大数据可使用 `core.RunDisk` 及 `RunOptions`。`core.ParseSpec` 和 `core.Validate` 使用现有规则解析器与规划器。调用不启动网页，也不调用 EXE。调用方需要根据操作系统和架构自行编译 Go 程序；源码包不能像 Java JAR 一样无需运行时或编译就直接执行。

目前 Go SDK 是文件型接口，Core 运行上下文取消、稳定版本兼容承诺以及 Java/Python 同进程原生内核或动态库尚未提供。Java/Python 进程客户端需要部署相应平台的 Core 可执行文件；不能声称它们支持无 EXE 的直接库调用。生产使用仍需真实规则、Driver、业务对账及目标环境验收。

## 接入前必须核实的数据

- 金额文件：每个业务坐标的原始金额、科目和期间，及币种、金额单位、可接受精度。
- 规则：各科目的来源筛选、阶段依赖、目标集合、比例及未命中来源的处理方式。
- Driver：每条规则、每个有效期间和目标成员对应的实际权重及数据版本；不得根据分摊结果反推或虚构。
- 层级与成员：从原系统导出完整父子关系、有效期间及成员集合，确认筛选和展开范围。
- 独立参考结果：与本次计算具有相同业务范围、期间和业务坐标的原系统结果，以及其他规则对范围的影响说明。

若缺少这些定义，表头完整或金额守恒也不能证明业务分摊正确。现有 Driver 覆盖检查仅对支持的起始阶段给出结果；含层级、来源筛选、Driver 筛选或后续阶段时，会明确标记尚未验证并列出所需导出项。分摊未命中来源可能按 Core 原规则透传，必须由业务核实是否符合预期。

运行失败提示保留本次的原始错误及可确认的来源池、阶段、因子；Driver 文件名只依据该次运行捕获的快照映射，不能通过当前已修改的模板反推。修复之后仍须重新运行并独立对账。

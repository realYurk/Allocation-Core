## 3. 优点（保留）

1. **版本身份处理是正确取舍**。冻结核心里的 `help=V20`、`run_summary=0.18.0`、`/healthz=0.14` 三处旧字符串**故意不改**——改了就会破坏 156 文件 SHA 冻结。改为在发行元数据层（`RELEASE_IDENTITY.json`）统一，并显式声明这些旧字符串的层级含义。这是"不能碰核心"约束下的最优解。
2. **容量预检保守且诚实**。明确标注"不是精确预测、不是 OS 配额"，给出 `critical_limitations` 四点边界，不夸大能力。
3. **输入快照的防篡改设计扎实**。复制前后双向哈希校验（`hash_before != hash_after` 捕获复制过程中被并发修改），拒绝覆盖已存在目标、拒绝目标在 root 内、拒绝绝对路径数据集。
4. **客户端原子下载逻辑正确**。`os.replace` / `ATOMIC_MOVE`（带回退）+ `finally` 清理临时文件，异常时绝不破坏已存在的有效文件。

## 4. 尚存的边界（非缺陷，但上线前必须做功课）

这些发行方自己也在文档里诚实声明了，我独立确认属实：

1. **容量预检必须挂在每条生产路径上**。`--exec` 启动才受覆盖，直接 CLI/HTTP 提交会绕过它。生产要在服务调度层调用预检 + 独立磁盘卷 + OS 磁盘配额。
2. **Content-Length 缺失时客户端无法自证完整**。文档建议另外校验文件 SHA/manifest，这是对的——分块传输下客户端只能"尽力写"，无法确认全量。
3. **HTTP 状态字段分层**。`/v1/jobs/{id}` 顶层 `status`（PASS/FAILED/RUNNING）与 `summary.status`（引擎内部 PASS）是两个不同层次。运维监控应以顶层 `status` 为准，别把 `summary.status` 当任务终态。（本轮测试中我一度因混淆两者误判，特此澄清。）
4. **真实数据库装载未压测**。SQL 模板的 MySQL/SQL Server/Oracle 方言仍需项目方按库验证，只有 SQLite 教学示例端到端验证过。

## 5. 总结

V21.1 是一次**高质量、对得上号的修复**：上一轮我提的 5 个缺点，5 个都有明确处置，且每个处置都经过了可复现的验证。没有发现算错钱、损坏证据、路径穿越、下载残缺的新问题。核心计算引擎 V20 冻结不变，156 文件 SHA 一致，财务正确性沿用前几轮已验证的结论。

唯一需要持续警惕的，仍是那个**工程性而非正确性**的问题：**导出体积 = 金额池数 × 每池有效目标数**，容量预检是"护栏"不是"自动刹车"，真正的安全要靠生产侧的磁盘配额和任务超时来兜底。

# Allocation Core V17 严苛测试报告（判官视角）

测试日期：2026-10-23
被测程序：`alloc_windows_amd64.exe`（V17，go-core/0.16.0）
测试机器：Intel i5-12490F（6 核 12 线程）、16 GB 内存、Windows
数据：全部为脚本合成虚构数据。

这一轮测试的目的是**找问题**，不是夸。分四块：计算正确性边界、V17 导出大数据、潜在 bug 挖掘、以及千万级全链路。

## 一、总体结论

**没有发现会产生错误金额或错误数据的 bug。** 计算内核和 V17 新增的证据工具在正确性、完整性、防篡改上都经得起检验。真正值得警惕的不是"算错"，而是三个工程性代价：**输出体积大、审计打包/校验要额外 CPU 和磁盘、trace 索引必须在使用前先建且过期会失效**。

## 二、计算正确性边界测试（13 项全过）

| 测试项 | 结果 | 说明 |
|---|:--:|---|
| 精度 0（整数元）三等分 | PASS | 100 → 33/33/34 |
| 精度 6（微单位）最小单位拆分 | PASS | 0.000001 分给 2 个，1 个得 1 单位、另 1 个为 0 被省略 |
| 大额 9 万亿守恒 | PASS | 9,000,000,000,000.00 精确守恒 |
| 零权重目标 | PASS | 权重为 0 的目标正确排除 |
| 全零驱动拒绝 | PASS | 分母为 0 明确报错，不产出半成品 |
| 负驱动（未授权）拒绝 | PASS | 报 "requires ALLOW_SIGNED" |
| 7 路余数分配 | PASS | 100/7 → 3 个 14.28 + 4 个 14.29，总额精确 |
| 两阶段奇数拆分守恒 | PASS | 100 → 3 系列 → 6 商品，端到端精确 |
| 负金额带符号守恒（上轮） | PASS | -100 对半分 |

要点：引擎用 int64 最小单位 + 最大余数法，余数分配确定且可复现；金额为 0 的行会被省略（不是 bug，是设计）；分母为 0、负驱动这类非法输入都会被明确拒绝而非静默算错。

## 三、V17 导出功能大数据测试（重点）

### 3.1 压缩与恢复（1200 万行，ledger 3.02 GiB）

| 指标 | 数值 |
|---|---:|
| 原始审计集总大小 | 4.37 GB |
| audit-pack 压缩后 | **431 MB** |
| 压缩率 | **89.65%** |
| audit-pack 耗时 | 16.5 s |
| audit-verify 耗时 | 9.6 s |
| audit-extract 耗时 | 16.9 s |
| 恢复后逐字节一致 | 是 |

- 无损：恢复出的 6 个文件与原始文件 SHA-256 完全一致，一字节不差。
- 防篡改：把 ZIP 里 ledger 区域翻转一个字节，`audit-verify` 立即报 "zip: checksum error" 拒绝。
- 防覆盖：`audit-extract` 到已存在目录会拒绝，不会静默覆盖。

### 3.2 trace-index 查询加速（120 万行实测）

| 操作 | 耗时 |
|---|---:|
| 无索引单行血缘查询（全表扫描） | 2.58 s |
| 建索引（一次性） | 1.08 s |
| 有索引单行血缘查询 | **0.013 s** |
| 加速比 | **199 倍** |
| 索引前后追溯结果一致性 | 逐字节一致 |

1200 万行下建索引 10.8 s、校验 2.5 s。查询速度的代价是一次性的建索引时间和约 29 MB 的索引存储。

### 3.3 大数据下的正确性核验（独立交叉验证）

- 1200 万行 `results.csv` 逐行求和 = 1,200,000.00，精确等于输入总额。
- 3600 个金额池的 `reconciliation.csv` 全部 PASS，零失败。

## 四、潜在 bug 挖掘（11 项全过）

最关键的几个（针对最容易出 bug 的地方）：

| 场景 | 结果 | 意义 |
|---|:--:|---|
| SKU 名含逗号 + 双引号 `商品"A,特殊"` | PASS | CSV 引号转义下 trace-index 的字节偏移仍正确 |
| SKU 名含换行符 `商品\n跨行` | PASS | 引号内换行是最难的 offset 场景，正确 |
| 无合格驱动的空结果 | PASS | 干净报错，不产出半成品目录 |
| 路径穿越防护（ZIP 内非法路径） | PASS | 已由 v17_test.go 覆盖 |
| 索引分片损坏拒绝 | PASS | 单字节翻转被拒，不静默返回不完整血缘 |
| 索引过期拒绝 | PASS | 文件时间戳变化即拒用 |

含换行符和引号的 SKU 能正确走通 trace-index，说明 `InputOffset()` 处理引号内多行记录的方式是对的——这是这类字节偏移索引最经典的翻车点，V17 过了。

## 五、发现的问题（诚实清单）

没有功能性 bug，但有几个**需要使用者注意的工程边界**，这些不是缺陷，是设计取舍：

1. **ledger.csv 体积巨大**：约 264 MB / 百万终端行。1200 万行 = 3.02 GiB。这是当前最大的实用障碍，下游存储和磁盘必须提前规划。
2. **audit-pack 是事后步骤，不加速计算**：16.5 s 打包 + 9.6 s 校验是额外开销。压缩省的是"长期存储"，不是"运行时间"。
3. **trace-index 需要先建才能快**：首次查询前必须先 `trace-index`，且证据文件一旦变化（哪怕只是改了时间戳）索引就失效，需要重建。高频变动场景下要权衡。
4. **磁盘空间是硬约束**：单次千万级全链路（生成 + 计算 + 打包 + 恢复）峰值占用接近 10 GB。本次测试磁盘可用 9.3 GB，勉强跑完。
5. **未覆盖**：断电/中途 kill 的可靠性、数据严重倾斜（单池几百万目标）、上亿驱动行、10M+ 金额池的极端拓扑，仍未测。

## 六、可复现的测试脚本

`bench/` 下新增/更新四个脚本，都可独立复现：

| 脚本 | 用途 |
|---|---|


原始指标保存在 `bench/*.json`。

## 七、判官总结

- **准确度**：满分。金额精确到最小单位，守恒三重校验，余数分配确定可复现，跨线程结果逐字节一致。
- **数据量导出**：无损压缩 89.65%、防篡改、防覆盖、逐字节可恢复，质量高；但 3 GB 的 ledger 是现实负担。
- **计算性能**：千万行 32 秒、250 MB 内存，够用；瓶颈在 IO 不在 CPU。
- **V17 新功能**：trace-index 和 audit-pack 都实现了它们承诺的东西，且边界处理（引号/换行/篡改/过期）扎实。

**结论：这版可以放心上生产前验收。** 没有发现会算错钱或损坏数据的 bug。唯一要提前做的功课是磁盘容量规划（ledger 体积）和索引/归档的生命周期管理。

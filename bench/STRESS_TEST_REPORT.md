# Allocation Core 性能与准确度实测报告

测试日期：2026-10-23
测试机器：Intel Core i5-12490F（6 核 12 线程）、16 GB 内存、Windows
被测程序：`alloc_windows_amd64.exe`（仓库内预编译二进制，Go 引擎 go-core/0.16.0）
数据：全部为脚本合成的虚构数据，不含任何真实业务资料。

## 一、结论先说

这个引擎在"准确度"上表现非常扎实，在"性能"上对百万到千万行级别够用且内存占用很低，但有一个容易被忽视的代价：**输出文件（尤其 ledger.csv）体积很大**，真正限制吞吐的往往不是计算，而是磁盘写入。

三个关键词：

- **准确度：满分。** 精确到分、余数分配正确、多因子/负金额/多阶段全部守恒，且结果可逐字节复现。
- **性能：够用。** 千万行（1200 万终端行）单机 32 秒，内存仅 250 MB。
- **实用程度：中上。** 作为计算内核很强，但大规模场景的 ledger 文件动辄数 GB，需要下游存储和磁盘规划。

## 二、性能数据

### 2.1 规模梯度（内存模式，4 线程）

| 场景 | 终端行数 | 金额池数 | 耗时 | 峰值内存 | 状态 |
|---|---:|---:|---:|---:|:--:|
| 24 万行 | 240,000 | 720 | 0.93 s | 39 MB | PASS |
| 120 万行 | 1,200,000 | 3,600 | 3.60 s | 48 MB | PASS |
| 600 万行 | 6,000,000 | 3,600 | 16.4 s | 135 MB | PASS |
| **1200 万行** | **12,000,000** | 3,600 | **31.8 s** | **250 MB** | PASS |

吞吐基本线性：行数翻倍，耗时大致翻倍。每 100 万终端行约 2.7 秒。

### 2.2 并发扩展（600 万行，内存模式）

| 线程数 | 耗时 | 峰值内存 |
|---:|---:|---:|
| 1 | 28.8 s | 110 MB |
| 4 | 16.4 s | 135 MB |
| 8 | 14.3 s | 207 MB |

4 线程相对单线程加速约 1.76 倍，8 线程相对 4 线程只再快 13%。这台机器只有 6 个物理核，且超过 4 线程后瓶颈从 CPU 转向内存带宽和磁盘 IO，所以 4 线程是这个场景下的甜点。引擎内部还会把 worker 数钳制在 `GOMAXPROCS*4` 和 32 的上限内。

### 2.3 内存模式 vs 磁盘索引模式（600 万行，4 线程）

| 模式 | 耗时 | 峰值内存 |
|---|---:|---:|
| 内存索引（默认） | 16.4 s | 135 MB |
| 磁盘索引 `--driver-disk-index` | 24.6 s | 55 MB |

磁盘索引用约 50% 的时间换 59% 的内存下降。当驱动数据量巨大、内存吃紧时值得开；否则默认内存索引更快。

### 2.4 多因子（600 万池 × 双驱动 = 1200 万终端行）

| 场景 | 终端行数 | 耗时 | 峰值内存 |
|---|---:|---:|---:|
| 单因子 | 6,000,000 | 16.4 s | 135 MB |
| 双因子（60% + 40%） | 12,000,000 | 32.7 s | 246 MB |

多因子会把每个池拆成多份再各自分配，终端行数翻倍，耗时和内存也相应翻倍。这是"同一 SKU 多行"的来源，不是重复入账。

## 三、准确度验证

用一个独立脚本构造**已知答案**的小样例，跑引擎后逐条断言。11 项全部通过：

| 测试项 | 结果 |
|---|:--:|
| 3:1 精确分配（100 元 → 75.00 / 25.00） | PASS |
| 总额守恒（100.00 → 100.00） | PASS |
| 三等分最大余数（100 → 33.33 / 33.33 / 33.34） | PASS |
| 余数只落在一个人头上一次（33.34 恰好一次） | PASS |
| 多因子 60/40 拆分后再分配（A=B=50.00） | PASS |
| 多因子总额守恒 | PASS |
| 不同线程数结果逐字节一致（1 线程 vs 4 线程） | PASS |
| 负金额带符号守恒（-100.00） | PASS |
| 负金额对半分（-50.00 / -50.00） | PASS |

另外在 1200 万行的大结果上做了独立交叉核验：`results.csv` 逐行求和 = 1,200,000.00，精确等于输入总额；`reconciliation.csv` 的 3600 个金额池全部 `PASS`，零失败。

### 准确度的技术保障

- **整数运算**：金额用 int64 最小货币单位（precision 0–6 位），不经过浮点，规避了 0.1+0.2≠0.3 这类尾差。
- **确定性余数分配**：最大余数法（largest remainder），余数按余数大小排序后逐个分配，同权重时按目标 ID 排序打破平局——所以结果可复现。
- **三重守恒校验**：每个金额池守恒 → 每个阶段守恒 → 整个 DAG 最终总账守恒。任何一层对不上直接报错，不产出半成品结果。

## 四、实用程度评估

### 做得好的地方

1. **内存占用极低**。千万行只要 250 MB，普通笔记本也能跑。这得益于"一池一批"的有界内存设计，内存只和并发批大小有关，和总行数无关。
2. **结果可审计**。`ledger.csv` 记录每个结果的驱动、分母、比例；`lineage_links.csv` 保证合并行不丢上游证据；`reconciliation.csv` 是守恒的直接证据。财务对账三件套齐全。
3. **确定性**。同一输入、不同线程数跑出来的结果文件 SHA-256 一致，适合做回归测试和审计留痕。
4. **可选磁盘索引**。内存吃紧时能主动降内存，给了部署弹性。

### 需要注意的代价和边界

1. **输出文件体积大**。这是最大的实际问题：
   - 1200 万行：`results.csv` 约 1.2 GB，`ledger.csv` 约 **3.2 GB**。
   - 多因子 1200 万行：`ledger.csv` 约 3.2 GB。
   每 100 万终端行，ledger 约占 264 MB。上亿行时 ledger 会到几十 GB，下游数据库和磁盘要提前规划。
2. **磁盘空间是硬约束**。本次测试单次千万级运行产生的输入 + 输出接近 4 GB，磁盘模式还要额外 spool 中间文件。
3. **吞吐瓶颈在 IO，不在 CPU**。从 4 线程到 8 线程提升有限，说明写 CSV（尤其大 ledger）才是千万级以上的主要耗时点。
4. **尚未测的**：本次是单机、单工厂、两系列、两阶段的规整数据。数据严重倾斜（单个池塞进几百万目标）、上亿驱动行、10M+ 金额池的极端拓扑，以及断电/中途 kill 的可靠性，都没有覆盖。这些属于下一轮压测的范围。
5. **`trace` 是顺序扫描**。单行回溯没问题，但高频全量血缘查询需要另建索引，引擎目前没做。

## 五、给使用者的建议

- **默认 4 线程、内存索引**。对大多数场景是最快最省心的组合。
- **内存紧张时**开 `--driver-disk-index --disk-partitions 16`，用约一半的速度换近六成内存。
- **上亿行前先算账**：先估 ledger 体积（约 264 MB / 百万行），确认磁盘和下游存储能装下，再决定要不要分批或压测。
- **别把 CSV 行数当 SKU 数**：多因子下一个 SKU 会占多行，展示时要按维度归并。
- **接生产前先跑守恒核验**：`reconciliation.csv` 全 PASS 是底线，`doctor` 通过不等于能算对，得真跑一遍。

## 六、复现方法

仓库 `bench/` 下新增三个脚本，都可独立复现：

- `gen_stress.py` — 生成指定规模（期间 × 科目 × SKU）的合成数据。
- `run_stress.py` — 跑单次压测，采集耗时、峰值内存、守恒结果。
- `correctness_test.py` — 正确性/准确度断言（11 项）。

示例：

```bash
# 生成 1200 万行数据
python gen_stress.py data --periods 12 --accounts 100 --skus 10000

# 跑压测
python run_stress.py --exe alloc_windows_amd64.exe --datadir data \
    --periods 12 --accounts 100 --skus 10000 --workers 4

# 正确性断言
python correctness_test.py --exe alloc_windows_amd64.exe
```

压测原始指标保存在 `bench/res_*.json`（8 组）。

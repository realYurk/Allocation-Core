## 三、性能与存储数据

### 计算：gzip 输出 vs 明文输出

| 规模 | 模式 | 耗时 | 峰值内存 | ledger 体积 |
|---:|---|---:|---:|---:|
| 600 万行 | 明文 | 17.25 s | 134 MB | 1.58 GB |
| 600 万行 | **gzip** | **21.46 s** | 136 MB | **115 MB** |
| 1200 万行 | 明文 | 31.85 s | 250 MB | ~3.17 GB |
| 1200 万行 | **gzip** | **41.69 s** | 252 MB | **229 MB** |

**关键发现**：

1. gzip 模式用约 **+24% 时间**，换来 ledger **93% 体积缩减**（1.58GB→115MB），性价比极高。
2. 内存几乎不涨（gzip 是流式 BestSpeed，不缓存明文）。
3. gzip 模式用 `gzip.BestSpeed`，压缩率仍达 93%——因为 ledger 是高度重复的结构化 CSV。

### V19 压缩索引（1200 万行实测）

| 操作 | 耗时 | 峰值内存 |
|---|---:|---:|
| 建索引（含前置校验） | ~11 s | ~50 MB |
| 有索引单行 trace | **0.12 s** | ~10 MB |
| 全量校验 | 7.5 s | ~11 MB |
| 无索引全扫描 trace（120 万行参考值） | 2.58 s | ~13 MB |

- **加速比**：120 万行时 2.58s→0.013s（199 倍）；千万级有索引 0.12s，无索引全扫描需解压 3.17GB 明文等效，线性外推 25–30s，**加速 200 倍以上**。
- **索引体积**：1200 万行索引目录 **544 MB**（含分块副本 + 64 分片），是 ledger.csv.gz（229MB）的 2.4 倍。

## 四、发现的缺点（必须正视，非 bug）

1. **V19 索引是净增存储，不是省空间。** 千万行下，`trace_packed_v19/` 占 544MB，比原始 gzip 证据还大。文档自己也承认"这是额外空间"。如果只是归档不查血缘，别建索引。

2. **results.csv 不压缩。** V18 只压缩 ledger/source_to_pool/lineage 三个证据文件，`results.csv`（千万行 1.2GB）和 `reconciliation.csv` 保持明文以方便 Excel。所以"压缩证据"省的是 ledger（占比最大），不是全部输出。

3. **首次建索引不可能零成本。** 建索引要先完整校验 + 解压读取整个 gzip 证据，千万行约 11 秒。文档已明确，但实际使用时容易忽略。

4. **无索引查询在千万级是灾难。** 一旦没建索引，单行 trace 要解压 3GB 明文等效顺序扫描（25–30s）。这是 V19 的价值所在，但反过来也意味着**必须提前建索引**，否则查询路径不可用。

5. **版本号不一致（小瑕疵）。** 二进制 `help` 和 HTTP 服务启动横幅里，"Allocation Core" 后面的版本号一处写 V18、一处写 V19（`VERSION.txt` 和 README 已更新为 V19，但 `main.go` 的 help 字符串仍是 V18）。不影响功能，但会让人困惑。

6. **manifest 含时间戳，无法跨运行对比。** `evidence_stream_manifest.json` 记录了 `run_summary.json` 的哈希，而 run_summary 含 `StartedUTC` 时间戳，导致同一份数据两次运行的 manifest 不同。这本身合理（manifest 是完整性快照），但如果下游想用 manifest 做"去重/幂等判断"，会失效。

## 五、优点（予以保留）

1. **无损性做到了字节级。** rolling digest 在流式写入时累加明文 SHA，从不重读解压后的巨型 ledger，这是正确的工程取舍。
2. **篡改检测全面。** 存储哈希 + 明文哈希双重校验，manifest 反序列化有 `DisallowUnknownFields`、长度上限（1MB）、文件数校验，防了大部分注入。
3. **原子发布。** 索引构建到临时目录、成功后 rename，失败不发布半成品（`os.Rename` 目录级原子）。
4. **路径穿越防护。** 之前版本就有 `filepath.Base` 校验，V18/V19 沿用。
5. **查询正确性有兜底。** `scanPackedEvidence` 对每个候选都重新核对完整 CSV key（`trueKey == k`），防止哈希前缀碰撞导致的错查。
6. **确定性保持。** 计算产物在任意 workers 数下逐字节一致，gzip 输出也确定（BestSpeed + 固定 ModTime）。

---

## 六、使用建议

- **要省长期存储** → 用 `--evidence-gzip`，几乎零内存代价，ledger 缩 93%。
- **要查血缘** → gzip 输出后立刻 `trace-pack-index`，别等到要查才发现没索引（无索引千万级查询 25s+）。
- **只归档不查** → 别建索引，省下那 544MB 额外空间。
- **上线前** → 把 `main.go` 里 help 的版本号统一成 V19。
